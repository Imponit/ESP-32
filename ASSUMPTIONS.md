# ASSUMPTIONS — принятые решения по неясным местам спецификации

Каждое решение можно пересмотреть; блокирующих архитектуру вопросов не выявлено
(стек, модель данных и машина состояний зафиксированы в SPEC.md).

## Статусы и переходы

1. **Начальный статус заказа при ручном вводе — `new`** (не `draft`).
   `draft` зарезервирован под черновики из входящих каналов (MVP-3) и доступен
   в машине состояний (`draft → new`).
2. **`cancelled`** разрешён из статусов: `draft, new, needs_review, planned,
   assigned, sent_to_driver, accepted_by_driver, in_progress, postponed` —
   т.е. «из любого статуса до `completed`». Из терминальных
   (`completed, failed, refused, cancelled`) отмена невозможна.
3. **`POST /orders/{id}/assign-driver`**: если заказ в `new`, выполняются два
   перехода `new → planned → assigned` (оба пишутся в `order_events`,
   actor = dispatcher). Если в `planned` — один переход. Снятие назначения —
   тем же эндпоинтом с `driver_id: null` (`assigned → planned`).
4. **`postponed → new`**: диспетчер ставит новую дату через `PATCH /orders/{id}`
   и переводит заказ в `new` через `/transition`. Автоматического переноса даты нет.
5. Кнопки пакета в боте двигают и пакет, и его заказы:
   «Принял» — пакет `sent → accepted`, заказы `sent_to_driver → accepted_by_driver`;
   «Начал маршрут» — пакет `accepted → started`, заказы → `in_progress`,
   водитель `work_status = on_route`;
   «Завершил маршрут» — пакет `started → finished`, водитель `work_status = idle`
   (статусы заказов не трогаются — они уже терминальные или останутся висеть
   как проблемные в сводке дня).

## Данные

6. **`day_part` пакета** использует значения `any | first_half | second_half`
   (совместимо с `time_window_type` заказа, без `exact`).
7. **Снапшот district**: `orders.district_id` копируется из адреса при создании
   заказа; при смене адреса заказа (PATCH с новым `address_id`) снапшот-поля
   перекопируются с нового адреса/клиента.
8. **`payment_status`**: `paid`, если `paid_amount >= total_amount`; `partial`,
   если `0 < paid_amount < total_amount`; иначе `unpaid`. Метод платежа из бота
   «Карта-перевод» пишется как `cashless`, «Без оплаты» — платёж не создаётся.
9. **Удаления нет нигде** (заказы/клиенты/адреса) — только деактивация или
   `cancelled`. Историчность важнее.
10. Телефоны храним строкой как ввели; поиск по клиентам — подстрока по имени
    и нормализованному номеру (только цифры). Жёсткой валидации формата нет (MVP-2 — дедупликация).

## Авторизация

11. JWT — HS256, секрет `JWT_SECRET` из `.env`, срок жизни 12 часов
    (рабочая смена диспетчера). Refresh-токенов в MVP-1 нет.
12. Пароли — **bcrypt** (библиотека `bcrypt`, без passlib — passlib не
    поддерживается и конфликтует с новыми версиями bcrypt).
13. Создание пользователей — только seed/админ (эндпоинт `POST /users` не в
    спецификации — отложен; пользователи создаются seed-скриптом). TODO MVP-2.

## Ссылки Яндекс.Карт

14. Точка с координатами: `https://yandex.ru/maps/?pt={lon},{lat}&z=17&l=map`;
    без координат: `https://yandex.ru/maps/?text={адрес urlencoded}`.
15. Маршрут: `https://yandex.ru/maps/?rtext={lat},{lon}~...&rtt=auto`
    (порядок точек = `route_position`, заданный диспетчером). Точки без
    координат в маршрутную ссылку не попадают; если таких точек нет вообще —
    `route_url = null`, у каждого заказа остаётся своя ссылка по тексту адреса.

## Бот и фоновые задачи

16. В dry-run бот-сервис стартует, пишет в лог `DRY RUN: polling отключён` и
    просто живёт (healthcheck-цикл); реальный polling включается только при
    наличии токена и `TELEGRAM_DRY_RUN=0`.
17. Отправка пакета из backend идёт через интерфейс `TelegramClient`;
    реализации: `DryRunTelegramClient` (лог), `AiogramTelegramClient` (реальная),
    `MockTelegramClient` (тесты, копит сообщения в списке).
18. `TaskRunner`: интерфейс с реализацией `BackgroundTasksRunner` поверх
    FastAPI `BackgroundTasks`. Отправка в Telegram выполняется фоном.

## Инфраструктура

19. Python-код совместим с 3.11+ (в Docker-образе — 3.12, как в SPEC;
    в среде разработки доступен 3.11 — синтаксис 3.12-only не используется).
20. Тесты: unit-тесты домена — без БД; тесты сервисов/API — SQLite
    (aiosqlite) in-memory, продакшен — только PostgreSQL (asyncpg).
21. Seed-учётки (только для разработки): `admin / admin123`,
    `dispatcher / dispatcher123`.
22. Настройка `timezone`, `max_route_points` и `geocode_confidence_threshold`
    читаются из таблицы `settings` с дефолтами `Europe/Moscow`, `9` и `0.7`.
23. Frontend в dev-режиме ходит в backend через Vite proxy (`/api`); в
    docker compose — nginx раздаёт статику и проксирует `/api` на backend.

## Геокодинг (MVP-2, раздел 11)

24. Провайдер по умолчанию — Яндекс.Геокодер (`https://geocode-maps.yandex.ru/1.x/`).
    Ключ — только из `.env` (`YANDEX_GEOCODER_API_KEY`). Нет ключа — геокодинг
    выключен: `POST /addresses/{id}/geocode` отвечает `503`, координаты вводятся
    вручную, как в MVP-1.
25. Ключ кэша (`geocode_cache.query_normalized`) — нормализованный `raw_address`:
    нижний регистр, схлопнутые пробелы, без хвостовой пунктуации. Совпал ключ —
    к провайдеру не ходим, берём из кэша.
26. Точность Яндекса → уверенность 0..1: `exact=1.0, number=0.9, near=0.7,
    range=0.6, street=0.5, other=0.3`. Порог — `geocode_confidence_threshold`
    (по умолчанию `0.7`); результат ниже порога считается неточным.
27. Поведение `geocode_status` при геокодинге: получены координаты → `ok`;
    адрес не найден → `failed`; провайдер недоступен (сеть/5xx/таймаут) → `pending`
    (данные не теряем, можно повторить); ручные координаты (`manual`) и уже
    проставленные координаты не перетираем без `?force=1`.
28. Неточный результат (ниже порога) переводит заказы этого адреса из `new` в
    `needs_review` через машину состояний (actor=system) — это «очередь проверки
    диспетчером». Заказы в других статусах не трогаем.
29. Эндпоинт геокодинга синхронный (один адрес — один вызов). Массовый геокодинг
    очередью/`TaskRunner` — при необходимости позже.

## Импорт заказов CSV/XLSX (MVP-2, раздел 8)

30. Поддерживаются `.csv` (разделитель `,`/`;`/таб — автоопределение, кодировка
    UTF-8/UTF-8-BOM) и `.xlsx` (openpyxl). Заголовки распознаются по синонимам
    (рус/англ), регистр и лишние пробелы игнорируются.
31. Обязательные колонки: `имя`, `телефон`, `адрес`, `дата`. Остальные —
    опциональны. Дата принимается в форматах `ГГГГ-ММ-ДД`, `ДД.ММ.ГГГГ`, `ДД/ММ/ГГГГ`.
32. Клиент ищется по нормализованному телефону (find-or-create), адрес — по
    нормализованному тексту в пределах клиента. Заказ создаётся со снапшотом,
    `source_type=import`. Дедупликация существующих карточек (слияние) — отдельный
    пункт MVP-2, здесь не выполняется.
33. Район указывается названием и матчится по справочнику (без учёта регистра);
    неизвестный район — ошибка строки. Пустой район допустим (district_id = null).
34. Ошибочные строки изолированы через SAVEPOINT (`begin_nested`): сбойная строка
    откатывается и попадает в отчёт (`errors[].row` — номер строки в файле, считая
    заголовок первой), валидные строки сохраняются.
35. `dry_run=1` — предпросмотр: файл полностью обрабатывается и валидируется, но в
    конце транзакция откатывается; `order_ids` в ответе пустой.

## Дедупликация клиентов (MVP-2, раздел 3)

36. Слияние карточек не удаляет источник (см. п. 9): добавлено поле
    `clients.merged_into_id` (FK на `clients`) — надгробие со ссылкой на основную
    карточку. Слитые карточки скрыты из поиска `GET /clients` и из поиска дублей.
37. Сигналы дублей: одинаковый нормализованный телефон, совпадающее
    нормализованное имя, общий нормализованный адрес. Группы с одинаковым набором
    участников объединяются, причины суммируются. Это кандидаты на ручную проверку
    диспетчером, а не автослияние.
38. При слиянии адреса, контакты (`client_contacts`) и заказы переносятся на
    основную карточку (`UPDATE ... client_id`). Снапшот-поля заказов
    (`phone/client_name/...`) не трогаются — историчность. Телефон источника, если
    отличается, сохраняется отдельным `client_contact` у основной карточки.
39. Известное ограничение (унаследовано из MVP-1, вне объёма дедупа): поиск
    `GET /clients?phone=` матчит по подстроке хранимого телефона, поэтому номера с
    разделителями (`700-00-11`) не находятся по слитной строке цифр. Кандидат на
    отдельную правку (нормализованная колонка телефона).

## Экспорт отчётов (MVP-2, раздел 8)

40. `GET /reports/export?date=&format=csv|xlsx`. CSV — детальная таблица заказов
    за день (с BOM UTF-8 для Excel). XLSX (openpyxl) — три листа: «Сводка»,
    «Касса по водителям», «Заказы». Неверный `format` → 400.
41. Имена районов/водителей в экспорте подтягиваются из справочников по id;
    район у заказа берётся из снапшота (`orders.district_id`).

## Баллы водителей (MVP-2, раздел 14)

42. Коэффициенты — в настройке `scoring_rules` (settings JSON), не в коде; при
    отсутствии берутся дефолты `core/scoring.py` (completed +1, бонус за день без
    failed +2, failed без причины −2, просрочка exact −1, refused 0).
43. «failed без причины» = переход в `failed` с пустым комментарием. Машина
    состояний требует комментарий для `failed`, поэтому на практике штраф почти не
    срабатывает — правило защитное и настраиваемое.
44. «День без failed» = дата доставки, где у водителя есть хотя бы один
    `completed` и ноль `failed`. Просрочка считается только для `exact`-окна:
    `completed_at` (в таймзоне из настроек) позже `time_window_to`.
45. Таблица `driver_scores` хранит сохранённый снимок за период (`POST
    /drivers/scores/save`); основной расчёт всегда идёт «на лету» по
    orders/order_events (`GET /drivers/scores`).

## Журнал событий (MVP-2, раздел 9)

46. `GET /events` — лента `order_events` (без новой таблицы, источник истины —
    `order_events`). Фильтр по дате — по `func.date(created_at)` (в UTC; для
    панели достаточно). Сортировка — новые сверху, пагинация limit/offset.
47. События обогащаются контекстом заказа (клиент/адрес из снапшота) и именем
    актора: диспетчер — из `users`, водитель — из `drivers`, иначе «система».

## Сдача кассы (MVP-2, раздел 13)

48. Отметка «сдал кассу» — таблица `cash_handovers` с уникальностью
    `(driver_id, handover_date)`; наличие записи = касса сдана. `amount` (фактически
    сдано) и `comment` опциональны. Запись upsert-ится при повторной отметке.
49. Дневной отчёт (`GET /reports/daily`) добавляет к каждому водителю в кассовой
    части `cash_handed_over` и `handover_amount`. Снять отметку — `DELETE`.

## Поиск по телефону (правка)

50. У клиента есть колонка `phone_normalized` (только цифры; 11-значные с ведущей
    7/8 → 10 цифр), заполняется автоматически из `phone_primary` через
    SQLAlchemy-валидатор. Поиск `GET /clients?phone=` идёт по ней — разделители в
    номере больше не мешают. Нормализация телефона централизована в
    `app/core/phones.py` (используется в поиске, дедупликации, импорте, боте).
