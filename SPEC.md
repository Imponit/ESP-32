# Спецификация: CRM/диспетчерская система для доставки воды 19 л

Нужно разработать CRM/диспетчерскую систему для бизнеса доставки питьевой воды в 19-литровых бутылях.

Цель системы: собрать заявки клиентов в одну базу, обработать их, распределить по дням, районам, временным окнам и водителям, отправить водителям задания через Telegram, получить обратную связь по выполнению и оплате, сформировать статистику и кассу за день.

## 0. Принципы выполнения

1. Работай поэтапно. Сейчас реализуй только **MVP-1** (раздел 3). Для функций MVP-2/MVP-3 создавай интерфейсы и места в проекте, но не реализуй их.
2. Не имитируй готовность. Нереализованное честно помечай `TODO` с готовыми интерфейсами.
3. Перед стартом задай вопросы только по тем решениям, которые блокируют архитектуру (если такие есть). Мелкие неясности решай сам и фиксируй каждое решение в файле `ASSUMPTIONS.md` в корне проекта.
4. Главный результат этапа — **проходимый сквозной сценарий приёмки** (раздел 15), а не количество файлов.

## 1. Контекст и масштаб

- Компания доставляет питьевую воду в 19-литровых бутылях (поликарбонат и ПЭТ), дополнительно — помпы.
- Клиенты: квартиры, дома, магазины, офисы. Оплата чаще всего при получении (наличные или перевод/карта).
- Один город. Районы (справочник, редактируется в настройках): Левобережный, Кальмиуский, Центральный, Приморский.
- Масштаб: до ~200 заказов в день в пик, 3–6 водителей, 1–2 диспетчера. Это небольшая нагрузка — архитектура должна быть простой: модульный монолит, без очередей сообщений и микросервисов.
- Таймзона: `Europe/Moscow` (вынести в настройки). Все «сегодня/завтра» считать в этой зоне.
- Язык интерфейса, данных и сообщений бота — русский. Валюта — RUB, суммы `DECIMAL(10,2)`.

### Источники заявок (по фазам)

- **MVP-1:** ручной ввод диспетчером.
- **MVP-2:** импорт CSV/XLSX.
- **MVP-3:** входящие сообщения клиентов — Telegram, SMS, MAX, WhatsApp, IP-телефония, Google Sheets — через единый интерфейс `IncomingChannelAdapter`, всё складывается в таблицу `incoming_messages`.

## 2. Стек (зафиксирован, не выбирай другой)

- Backend: **Python 3.12+, FastAPI**
- База: **PostgreSQL 16**. Координаты — обычные numeric-колонки `latitude/longitude`. **PostGIS не ставить** — он понадобится только на этапе оптимизации маршрутов (MVP-3).
- ORM: SQLAlchemy 2.x, миграции — Alembic.
- Telegram-бот: **aiogram 3.x**, отдельный сервис в Docker Compose.
- Frontend: **React + Vite (SPA)**, UI на русском. Next.js не использовать.
- Фоновые задачи (отправка в Telegram, в будущем геокодинг): встроенные средства — `BackgroundTasks`/asyncio-воркер внутри backend. **Celery/RQ/Redis не добавлять** — масштаб не требует. Заложи тонкий интерфейс `TaskRunner`, чтобы при росте заменить реализацию.
- Docker Compose: сервисы `db`, `backend`, `bot`, `frontend`.

### Деплой и режим работы

Целевой режим — **VPS, docker compose, работа 24/7**: бот должен принимать статусы от водителей вечером, когда компьютер диспетчера выключен. Локальный запуск того же compose — для разработки. Диспетчер работает через браузер. Никаких Electron/Tauri.

## 3. Дорожная карта

### MVP-1 — устойчивое ядро (реализовать сейчас)

1. Docker Compose, PostgreSQL, миграции Alembic, seed-данные.
2. Авторизация: JWT, роли `admin` и `dispatcher`. **Водители веб-аккаунтов не имеют** — они авторизуются в боте по Telegram ID.
3. Клиенты и адреса: создание, поиск, редактирование; район выбирается вручную; координаты можно ввести/поправить вручную.
4. Заказы: создание, редактирование, список на дату с фильтрами (район, часть дня, статус, водитель).
5. Водители: таблица с машиной и вместимостью, активация/деактивация.
6. Назначение заказов водителю, формирование маршрутного пакета (до 9 адресов).
7. Ссылки на Яндекс.Карты: на одну точку и на маршрут пакета.
8. Telegram-бот водителя: регистрация, получение пакета, статусы по заказам, фиксация оплаты. Режим dry-run без реального токена.
9. Машина состояний статусов заказа + история событий (`order_events`).
10. Дневной отчёт: заказы, бутыли, деньги по способам оплаты, касса по каждому водителю.

### MVP-2 — данные и автоматизация

1. Геокодинг через Яндекс: адаптер, кэш (`geocode_cache`), точность, очередь «требует проверки диспетчером».
2. Импорт заказов из CSV/XLSX.
3. Дедупликация клиентов по телефону/адресу/имени, слияние карточек.
4. Архив заказов, статистика по водителям за период, экспорт отчётов в XLSX/CSV.
5. Баллы водителей (правила — в настройках, не в коде).
6. Экран «Журнал событий» в панели.
7. Отметка «водитель сдал кассу» в дневном отчёте.

### MVP-3 — каналы и оптимизация

1. Входящие каналы: Telegram от клиентов, SMS, MAX, WhatsApp, IP-телефония — адаптеры на едином интерфейсе; Google Sheets.
2. Автоматическое извлечение данных из текста заявки (имя, телефон, адрес, дата, время, количество, комментарий), очередь черновиков на проверку.
3. Каталог товаров/услуг + таблица `order_items` (миграция с фиксированных полей заказа).
4. Оптимизация порядка точек маршрута: OR-Tools и/или Yandex Route Optimization API (интерфейс `RouteOptimizer` закладывается в MVP-1). При необходимости — PostGIS.
5. Расширенные KPI и аналитика.

## 4. Архитектура

Модульный монолит. Структура по слоям:

- `app/core` — домен и бизнес-логика: сущности, машина состояний, правила планирования, расчёт отчётов. **Не зависит** от FastAPI, aiogram, Яндекс API.
- `app/adapters` — внешний мир: `GeocoderProvider` (MVP-2), `TelegramClient`, `IncomingChannelAdapter` (MVP-3), `RouteOptimizer`.
- `app/services` — сценарии: planning, dispatch, reporting, scoring.
- `app/api` — FastAPI-роуты, схемы Pydantic, auth.
- `app/bot` — aiogram-бот (отдельный процесс), работает с доменом через service layer.
- `frontend/` — React SPA.

Требование живучести: при недоступном Telegram или геокодере система продолжает работать — данные остаются в базе, проблемные статусы видны, диспетчер работает вручную.

## 5. Модель данных

### Принцип снапшота

Заказ — исторический документ. При создании заказа в него **копируются**: `phone`, `client_name`, `district_id`, `entrance`, `floor`, текст адреса. Последующее изменение карточки клиента или адреса не меняет уже созданные заказы. Это сделано намеренно — не «нормализуй» эти поля.

### Таблицы MVP-1

`users`, `districts`, `clients`, `client_contacts`, `addresses`, `drivers`, `orders`, `route_batches`, `order_events`, `payments`, `settings`.

Таблицы MVP-2: `geocode_cache`, `driver_scores`. Таблицы MVP-3: `incoming_messages`, `message_sources`, `products`, `order_items`. Для них достаточно моделей-заготовок или просто плана в ERD.

Отдельной таблицы `delivery_tasks` **не делать**: один заказ = одна доставка, принадлежность пакету хранится в `orders.route_batch_id` и `orders.route_position`. Отдельной таблицы `audit_log` **не делать** — историю изменений заказов ведёт `order_events`.

### users

`id, login, password_hash (bcrypt/argon2), name, role (admin|dispatcher), is_active, created_at`

### districts

`id, name, is_active, sort_order`

### clients

`id, name, phone_primary, comment, created_at, updated_at` — дополнительные телефоны/контакты в `client_contacts (id, client_id, type, value, comment)`.

### addresses

`id, client_id, raw_address, normalized_address, latitude, longitude, geocode_status (none|pending|ok|failed|manual), geocode_confidence, district_id, entrance, floor, comment, created_at, updated_at`

В MVP-1 `geocode_status` принимает значения `none` или `manual` (координаты введены вручную); остальные значения задействует MVP-2.

### drivers

`id, name, phone, telegram_id (nullable, уникальный), is_active, work_status (idle|on_route), district_default_id, vehicle, capacity_bottles, comment, created_at`

`is_active` — административный флаг (работает/уволен), `work_status` — оперативный. Не смешивать их в одно поле.

### orders

`id, client_id, address_id, delivery_date, time_window_type (any|first_half|second_half|exact), time_window_from, time_window_to, district_id (снапшот), bottles_pc_qty, bottles_pet_qty, pumps_qty, floor (снапшот), entrance (снапшот), phone (снапшот), client_name (снапшот), comment, total_amount, payment_method_plan (cash|cashless|unknown), payment_status (unpaid|paid|partial), paid_amount, status, assigned_driver_id, route_batch_id, route_position, source_type (manual|import|telegram|sms|max|whatsapp|phone), completed_at, created_at, updated_at`

Состав заказа в MVP-1 — фиксированные поля количества (`bottles_pc_qty`, `bottles_pet_qty`, `pumps_qty`). Переход на `order_items` — только в MVP-3.

### route_batches

`id, delivery_date, day_part, district_id, driver_id, status (draft|sent|accepted|started|finished), route_url, sent_at, created_at`

### order_events

`id, order_id, event_type, old_status, new_status, actor_type (dispatcher|driver|system), actor_id, comment, created_at`

### payments

`id, order_id, driver_id, method (cash|cashless|other), amount, created_at`

### settings

Ключ-значение (JSON): `max_route_points` (по умолчанию 9), таймзона, правила баллов, токен бота (только ссылка на env), параметры геокодера.

## 6. Статусы заказа и машина состояний

Статусы: `draft, new, needs_review, planned, assigned, sent_to_driver, accepted_by_driver, in_progress, completed, failed, refused, postponed, cancelled`.

Разрешённые переходы (реализовать как явную машину состояний с функцией проверки `can_transition`, покрыть unit-тестами и разрешённые, и запрещённые переходы):

```
draft → new
new → needs_review | planned
needs_review → new | planned          (после проверки диспетчером)
planned → assigned
assigned → sent_to_driver | planned   (снять назначение)
sent_to_driver → accepted_by_driver
accepted_by_driver → in_progress
in_progress → completed | failed | refused | postponed
postponed → new                       (с новой датой доставки)
cancelled ← из любого статуса до completed
```

`needs_review` используется, когда не хватает данных или геокодинг неточен (актуально с MVP-2; в MVP-1 переход существует, но почти не используется).

При переходе в `completed` обязательно фиксируются `completed_at` и оплата (раздел 12). Переходы `failed` и `refused` требуют комментарий/причину. Каждый переход пишет запись в `order_events`.

Соответствие кнопок бота: «Выполнен» → `completed`, «Ошибка» → `failed`, «Отказались» → `refused`, «Перенос» → `postponed`.

## 7. Статусы водителя

- `is_active` (boolean) — административный: работает / не работает.
- `work_status`: `idle` | `on_route` — выставляется автоматически по кнопкам «Начал маршрут» / «Завершил маршрут».

Отдельную сущность «смена» (`driver_shifts`) в MVP **не делать** — дневная статистика строится по `order_events` и `payments` за дату.

## 8. API (REST, все списки с пагинацией `limit/offset`, OpenAPI/Swagger автоматически)

- `POST /auth/login` → JWT
- `GET /auth/me`

Справочники:
- `GET /districts`, `POST /districts`, `PATCH /districts/{id}`

Клиенты и адреса:
- `POST /clients`, `GET /clients?q=&phone=`, `GET /clients/{id}`, `PATCH /clients/{id}`
- `POST /clients/{id}/addresses`, `PATCH /addresses/{id}` (включая ручную правку координат и района)

Заказы:
- `POST /orders`, `GET /orders?date=YYYY-MM-DD&district_id=&part=&status=&driver_id=`, `GET /orders/{id}`, `PATCH /orders/{id}`
- `POST /orders/{id}/assign-driver`
- `POST /orders/{id}/transition` `{status, reason, comment}` — только через машину состояний
- `POST /orders/{id}/payment` `{method, amount}`

Водители:
- `GET /drivers`, `POST /drivers`, `PATCH /drivers/{id}`

Планирование и отправка:
- `POST /planning/batches` `{date, day_part, district_id, driver_id, order_ids[]}` — создать пакет (валидация: не больше `max_route_points`; предупреждение, если суммарно бутылей больше `capacity_bottles` водителя — предупреждать, не блокировать)

Отчёты:
- `GET /reports/daily?date=` — заказы по статусам, бутыли, суммы по способам оплаты, касса по каждому водителю, отказы с причинами, заказы `completed` без оплаты
- `GET /reports/export?date=&format=xlsx|csv` — MVP-2

Импорт:
- `POST /import/orders` — MVP-2

## 10. Telegram-бот водителя (aiogram 3, отдельный сервис)

Регистрация:
- `/start` → бот просит поделиться контактом (кнопка request_contact) → ищет водителя по номеру телефона → привязывает `telegram_id`. Если не нашёл — сообщает «обратитесь к диспетчеру», диспетчер привязывает Telegram ID вручную в карточке водителя.

Команды:
- `/today` — задания на сегодня
- `/status` — текущий статус и остаток заказов

Сообщение с пакетом: дата, часть дня, район, ссылка на общий маршрут, список заказов (адрес, клиент, кол-во бутылей, сумма, способ оплаты, комментарий, ссылка на точку). Кнопки пакета: «Принял», «Начал маршрут», «Завершил маршрут».

Кнопки по каждому заказу: «Выполнен», «Ошибка», «Отказались», «Перенос», «Комментарий», «Показать телефон» (просто показывает номер).

После «Выполнен» — шаг оплаты: «Наличные» / «Карта-перевод» / «Без оплаты»; сумма по умолчанию `total_amount`, водитель может ввести фактическую. Создаётся запись в `payments`, обновляются `payment_status`/`paid_amount`.

«Ошибка» и «Отказались» запрашивают короткий комментарий/причину. «Перенос» — заказ уходит в `postponed`, новую дату ставит диспетчер.

Опционально: приём геолокации водителя.

Все действия бота идут через service layer (та же машина состояний, те же `order_events`).

**Dry-run обязателен:** при `TELEGRAM_DRY_RUN=1` или отсутствии токена бот не ходит в Telegram API — исходящие сообщения пишутся в лог, проект полностью поднимается и тестируется без реального токена. Для тестов — `MockTelegramClient`.

## 11. Геокодинг (интерфейс — сейчас, реализация — MVP-2)

Интерфейс `GeocoderProvider`; реализации: `YandexGeocoderProvider`, `MockGeocoderProvider` (для тестов).

Правила:
- кэш по нормализованному адресу (`geocode_cache`);
- если координаты уже есть — повторно не геокодировать;
- хранить точность результата; при неточном результате — заказ в `needs_review`;
- при недоступном геокодере заказ не теряется: `geocode_status = pending|failed`;
- ручная правка координат доступна всегда (уже в MVP-1);
- все запросы к геокодеру логируются.

## 12. Маршруты

MVP-1:
- генерация ссылки Яндекс.Карт на одну точку (по координатам, при их отсутствии — по тексту адреса);
- генерация ссылки на маршрут пакета по координатам, максимум `max_route_points` точек (по умолчанию 9, настройка);
- порядок точек = порядок, заданный диспетчером (`route_position`), сохраняется.

Интерфейс `RouteOptimizer`:
- `SimpleRouteOptimizer` (MVP-1) — без оптимизации, группировка район + часть дня, порядок диспетчера;
- `OrToolsRouteOptimizer`, `YandexRouteOptimizer` — заглушки с интерфейсом, реализация в MVP-3 (учёт временных окон, вместимости, срочности).

---

## 13. Оплата и касса

- Оплата при получении — основной сценарий. Факт оплаты фиксирует водитель в боте при завершении заказа (раздел 10).
- Дневной отчёт по каждому водителю: выполнено заказов, доставлено бутылей, собрано наличными, получено картой/переводом, заказы `completed` без оплаты (расхождения).
- MVP-2: отметка «водитель сдал кассу» за дату.

---

## 14. Баллы водителей (MVP-2, правила — в настройках)

- `completed`: +1;
- бонус за день без `failed`;
- `failed` без причины: −2;
- просрочка (для `exact`-окна: `completed_at` позже `time_window_to`): −1;
- `refused` по причине, не зависящей от водителя: 0.

Коэффициенты хранятся в `settings` (JSON), не зашиты в код. Расчёт — по данным `order_events`/`orders`, отдельный сервис.
